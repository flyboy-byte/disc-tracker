# Proposal: hosting a Try Discs catalog download on this VPS

**For:** whoever reviews this on the VPS (a separate Claude Code session with direct box access,
or Logan directly). Written to be self-contained — no other context needed.

**Status (2026-08-17): reviewed on this VPS, clear to deploy — not yet deployed.** A VPS-side
Claude session reviewed this proposal against the box's real config. Verdict: the routes as
written are correct, `send_from_directory` was confirmed the right call over serving via nginx
directly (nginx runs as `www-data`; `/home/ubuntu/` is mode 750 `ubuntu:ubuntu`, so `www-data`
can't traverse in without a permissions change not worth making for this), and traversal /
`data/disc_tracker.db` / `.secret_key` exposure were all confirmed non-issues. One recommended,
**non-blocking** addition: this vhost has no `limit_req` zone at all (a pre-existing gap, not
introduced here) and the new `/catalog/` routes are the first unauthenticated surface on this
app — worth adding a rate limit alongside, not worth delaying deploy for:
```nginx
limit_req_zone $binary_remote_addr zone=disc_catalog:10m rate=10r/s;
# in the disc.flyboybyte.com server{} block:
location /catalog/ {
    limit_req zone=disc_catalog burst=20 nodelay;
    proxy_pass http://127.0.0.1:5757;
}
```
That's an nginx/VPS-config change, applied directly on the box (not through this repo's
`deploy.sh`). Everything else below is the original proposal, unchanged and confirmed accurate.

## What this is, in one paragraph

The Disc Tracker Android app currently bundles a static 1,660-disc library inside the app itself
(no network involved). We're adding an *optional* second, larger disc catalog (2,147 discs) from
a third party (Try Discs), licensed for this use, that the app can download on request. Their
data must never be committed to the public GitHub repo — instead it lives only on this VPS, and
the app fetches it directly. This doc proposes exactly how that hosting works.

## What's being added, precisely

**One new directory:** `~/disc_tracker/data/catalog/` — a subdirectory of the existing `data/`
folder this app already uses for its SQLite database and session secret key. Like the rest of
`data/`, it is `.gitignore`d — `git pull` will never create, modify, or delete anything in it.
Two files live here once populated: `manifest.json` (small, a few hundred bytes — version number,
source attribution, a SHA-256 hash) and a data file like `catalog-v1.json` (the actual disc
records, currently ~a few hundred KB as plain JSON).

**Two new Flask routes**, added to `app.py`:

```python
CATALOG_DIR = os.path.join(DATA_DIR, 'catalog')

@app.route('/catalog/manifest.json')
def get_catalog_manifest():
    return send_from_directory(CATALOG_DIR, 'manifest.json', mimetype='application/json')

@app.route('/catalog/<path:asset>')
def get_catalog_asset(asset):
    return send_from_directory(CATALOG_DIR, asset, mimetype='application/json')
```

Both are **public and unauthenticated** — no `@login_required`, no session cookie needed. This is
deliberate: the Android app has no website login/session concept at all, so these routes have to
be reachable with nothing but a plain HTTPS GET. `send_from_directory` is Flask's own safe
primitive for this — it resolves the requested filename against `CATALOG_DIR` and refuses
anything that would escape that directory (path traversal via `../` etc. gets a 404, verified
locally). Both routes 404 cleanly if the file doesn't exist yet (i.e., before the data is ever
published, hitting either URL just returns a normal 404 — no error, no crash).

That's the entire surface. **No query parameters, no search, no filtering, no listing endpoint.**
You can fetch `manifest.json` or one specific named file — nothing else is possible through this
API. That's a deliberate constraint carried over from the data provider's terms (below), not an
oversight — a future "let me search the catalog by name" endpoint would violate what we agreed to
and shouldn't get added here without revisiting that agreement first.

## How the data actually gets here (and why it's separate from normal deploys)

Code changes (the two new routes above) go through the completely normal path: `git push` →
`deploy.sh` → `git pull` on the VPS → service restart. Nothing new there.

The catalog **data** is different on purpose. It's generated by a local tool
(`tools/trydiscs-sync.js generate`, run on a developer machine, not on this VPS) using a private
API key that never leaves that machine, and gets pushed here with a plain `scp`:

```
scp manifest.json catalog-v1.json disc.flyboybyte.com:~/disc_tracker/data/catalog/
```

This is a manual, maintainer-run step (`node tools/trydiscs-sync.js publish`), run only when the
catalog is actually being updated — not on every deploy, not automated, not triggered by any web
request. It uses whatever SSH access `deploy.sh` already has to this box; no new credentials, no
new access path.

## Why this shape specifically — the terms we're operating under

Try Discs' founder (Azeem) granted access to this catalog with explicit conditions:

- The API key and the sync tooling stay private — never in the app, never in the public repo.
  (Already true — the key lives only as a local shell environment variable when the `fetch`
  subcommand runs; it's never written to any file in the repo.)
- The generated catalog itself must never be committed to GitHub. (This is *why* it lives in
  `data/catalog/` on this VPS instead of the repo — that directory is gitignored specifically so
  this can never happen by accident.)
- Using the catalog for the app's own lookup/search/suggestions/import/audit features is fine.
- The file **can** be publicly fetchable by the app itself, but must not be promoted or
  documented as a standalone downloadable dataset for other developers, and must not be exposed
  through a separate public search API.
- A linked "Disc data by Try Discs" credit is required in the Android app, the website, and the
  README. (Done in the Android app's Settings screen, conditional on a user actually having
  downloaded the catalog; done in the README; the website doesn't consume this data yet so no
  website credit has been added — would be misleading to credit a source with nothing behind it.)
- Before any Play Store / F-Droid submission, he wants a look at the final format, attribution,
  and update flow. (Store submission is separately, deliberately on hold for this whole project
  right now — this is a note for whenever that changes, not a blocker today.)

The two-fixed-endpoint, no-query-params design above is the direct implementation of "publicly
fetchable, not a public API" — it reads unambiguously as "download this specific file," not
"query this dataset."

## What this does *not* touch

- The existing SQLite database (`data/disc_tracker.db`) and session secret (`data/.secret_key`)
  — same directory tree, but untouched, unreferenced by the new routes, and not reachable through
  them (`send_from_directory` only serves files that exist directly inside `CATALOG_DIR`, and
  those two files live in the parent `data/` directory, one level up — a `../` attempt to reach
  them is exactly the path-traversal case `send_from_directory` blocks).
- Every existing route, including the currently-authenticated `/api/master` (the original bundled
  library, requires login) — unchanged.
- No new dependency. `send_from_directory` is part of Flask, already a dependency.

## Questions for the VPS-side review

These are genuinely open — answer with whatever this box's actual setup implies:

1. **Rate limiting.** This is the first fully public, unauthenticated route on this app (every
   other route requires a login). Nothing else on this site currently rate-limits requests. Is
   that worth adding here specifically, given it's now reachable by anyone with the URL, not just
   logged-in users?
2. **Reverse proxy / nginx specifics.** This repo has no nginx config in it — if this box fronts
   Flask with nginx or another reverse proxy for `disc.flyboybyte.com`, is there anything about
   that layer (caching, header handling, request size limits) that changes how these two routes
   should be written or configured, that wouldn't be visible from the Flask code alone?
3. **`send_from_directory` vs. static hosting.** Given this box's real request volume/setup, is
   routing this through the Python process the right call, or would serving `data/catalog/`
   directly via whatever's in front of Flask (if anything) be meaningfully better? Only matters
   if there's already a reverse proxy layer to hang it off of.
4. **General.** While in here — anything else about this VPS's current security posture worth
   flagging, unrelated to this specific change? This felt like a reasonable moment to ask.
